A form field declared DataType: 'Number' with InputType: 'Picker' — an entity foreign key, virtually always — showed a literal 0 on a brand-new form, as though something had been selected. Two libraries were candidates, so this section separates them.

Where the 0 comes from. A pict-section-form marshal reads values through manyfest's getValueByHash, which substitutes the descriptor default for any address the model does not hold yet. With no explicit Default that is manyfest's per-DataType default — and those differ: String gets '', but Number, Integer and Float get 0. So the value reaching the widget on a pristine form is 0, not empty. Computed live from manyfest alone, with no form in the picture:

Whose bug the display is. This demo app contains no pict-section-form and no dynamic form at all — the value is handed to the control with a plain setValue(0). The first picker above still paints 0. That settles it: the marshal was doing its job, and the display bug was the picker's — 0 was simply a value it had no way to know meant "nothing selected".

The fix. EmptyValues — a display-only list of values a host declares as "nothing selected", which the pict-section-form adapter seeds with [0] for a Number/Integer/Float descriptor. The second picker is the first one with it set. Use the buttons and watch the readout: both pickers store the same value at every step, and only the painted text differs — so a host's 0-means-unset stays a valid data pattern for solvers, exports and the API. The third picker shows the escape hatch: its option list contains a real option valued 0, so that is a genuine selection and shows its label even with EmptyValues: [0] set. Set a field's own PictForm.EmptyValues to override, or to [] to opt out entirely.
